# Техническое задание

## Общие положения

- Команды по ~3 человека.
- Выбор темы — проектирование сложной технической системы: БПЛА с определённой функцией, клиент-серверное приложение, высоконагруженная система, система управления технологическим процессом, система управления критическим инфраструктурным объектом.
- Темы можно выбирать на основании задач, выполняемых на текущем месте работы, при согласовании с руководителем.

В рамках решения рассматриваются этапы со стороны условного Заказчика на разработку системы и со стороны условного Исполнителя разработки.

## Со стороны Заказчика (при участии Исполнителя)

**1. Концепция безопасности продукта (КБП).** Формулируем текстом задачу системы, внешние по отношению к системе условия и взаимодействия, обеспечивающие её функционирование. Главное — перечислить в таблице ценности, с которыми взаимодействует система, негативные события, возникающие при нарушении этих ценностей, оценку ущерба при таком нарушении; в комментариях указать дополнительную информацию и возможные действия при нарушениях.

**2. Контекст.** Описываем в виде диаграммы состояний: как система взаимодействует с внешними компонентами, на основании формулировки из предыдущего пункта.

**3. Базовые сценарии использования системы.** Описываются в виде диаграммы последовательности на основании предыдущего пункта. Добавляем комментарии по особенностям взаимодействия: что можно делать с помощью системы.

## Со стороны Исполнителя

**1. High-Level Architecture (HLA) / Архитектура.** Здесь впервые появляется собственная архитектура системы. Описывается в виде диаграммы состояний из компонентов и взаимодействий между ними. Отдельной таблицей описываются компоненты системы с указанием назначения и дополнительных комментариев. Система представляется без учёта кибериммунного подхода, опираясь лишь на целевую задачу: какие компоненты нужны для выполнения задач системы.

**2. Базовые сценарии + HLA.** Подробнее описываем с помощью диаграмм последовательностей упомянутые ранее базовые сценарии: как они реализуются на базе архитектуры из предыдущего пункта, как с помощью данных компонентов выполнить задачи системы.

**3. Цели и предположения безопасности (ЦПБ).** Списком перечисляем отдельно цели безопасности и отдельно предположения безопасности. Каждая цель своей формулировкой должна описывать, что хотим достичь (состояние системы). Иными словами, она должна иметь форму утверждения, выполняться всегда и отвечать на вопрос «что?», а также содержать описание актива и ущерба, который она защищает. Предположения в схожей форме оговаривают внешние гарантии по отношению к системе, обеспечиваемые другими системами. Помним правило: для одной системы предположения — для другой цели, и наоборот.

**4. Негативные сценарии.** С помощью диаграмм последовательностей демонстрируем, как компрометация каждого из компонентов системы, определённых на этапе HLA, влияет на цели безопасности для каждого из сценариев. Иными словами, это диаграммы из раздела «Базовые сценарии + HLA», у которых поочерёдно «окрашиваем» компрометацией компоненты и демонстрируем влияние на другие компоненты и ЦБ. Снабжаем комментариями каждый такой сценарий. Обязательно рассмотреть негативные сценарии, нарушающие ЦБ.

**5. Политика архитектуры.** Финальное архитектурное решение, позволяющее при минимальных затратах обеспечить соблюдение всех ЦБ. С помощью диаграммы состояний путём расцвечивания распределяем компоненты системы в рамках представления Data Flow Diagram (DFD) по трём категориям доменов (недоверенный, доверенный, повышающий). Помним подход: максимум недоверенных, минимум доверенных и повышающих. Также снабжаем компоненты оценкой сложности/стоимости помещения в доверенный или повышающий домен. Снабжаем таблицей с комментариями по каждому компоненту: почему он отнесён в тот или иной домен, а также обоснованием оценки сложности/стоимости.

## Итог

Задача разработчиков — доказать Заказчику, что в рамках выбранной политики архитектуры перечисленные ЦБ достигаются всегда с учётом предположений безопасности. В идеале при описании политики архитектуры описываются все сообщения между компонентами, запросы и ответы, чтобы при применении дополнительных способов изоляции компонентов и мониторов безопасности в рамках MILS/FLASK можно было сразу определить их конфигурации.
